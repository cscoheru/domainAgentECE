## 2. 关于"持久上下文记忆"——codex 的架构立场（回应 user 的问题）

### 2.1 先把三个被混用的概念拆开

| 层 | 是什么 | 现状 | 生命周期 |
|---|---|---|---|
| **会话凭据** | cookie / token：证明"这次请求是谁发的" | 用的是 **Onyx 的 session cookie**（借来的身份） | 短效、可撤销 |
| **身份 identity** | 用户是谁、属哪个组织/部门/角色 | ECE 有 `identity/parser.py`（`resolve_identity(x_user_id)`）+ `0007_user_orgs` 迁移；但**是 `X-User-Id` 头，不是登录** | 长期 |
| **持久上下文记忆** | 跨会话保存的、关于用户/组织/项目的事实与偏好，下次自动参与上下文组装 | **完全没有** | 长期（用户要求"一直保存"） |

user 要的是第三层。**而第三层要求第二层先成立**——"从第一次登录后"意味着 ECE 得有自己的登录与会话，而不是继续借 Onyx 的 cookie。这与 review 指出的"identity 穿透"债务是**同一个问题的两端**。

### 2.2 立场：记忆必须归 ECE，不能放 Onyx

- Onyx 侧确实有 `personalization.memories` / `enable_memory_tool`（`GET /api/me` 可见），但它是**引擎侧、无来源、无审计、不可迁移**的。
- 把用户上下文放在可替换引擎里，等于**把"用户上下文"这个核心 IP 交给可替换件**：换引擎即丢，且与 `AGENTS.md` §6 / CODEX-ROLE R1（ECE 拥有身份/权限/来源/审计）直接冲突。
- **可考虑的例外**：将来若需要，ECE 可以把**自己记忆里的子集**下发给引擎做个性化（单向、可撤销），但**系统 of record 永远是 ECE**。

### 2.3 形态建议（第一版）

1. **记忆是一等领域对象**：`owner`（user/org/team）、`scope`、`statement`、`source`、`created_at`、`confidence`、`expires_at`。复用 `context/provenance.py` 的来源追踪思路。
2. **写入过权限引擎**：谁能写/读/删谁的记忆，走既有 `permissions/engine.py`（不是新造一套）。
3. **读取进 context assembly**：作为管道里的显式一步，**位置必须在权限判定之后**（否则重蹈"后置过滤"的侧信道坑）。
4. **合规三件套是前提而非附加项**：可查看、可删除（单条 / 全量）、可追溯（来源 + 时间 + 谁写的）。没有这三件，"永久保存"是负债而不是资产。
5. **第一版不做 LLM 自动抽取**：自动抽取不确定，无法做确定性验收（沿用 OEI-007 立下的规矩）。第一版做**显式记忆**（用户/管理员显式声明）+ 自动注入 + "本次回答用到了哪几条记忆"的可见性。

## 3. 采纳后的排期建议（编号不变、不插刀、不顺延）

## 5. 第二轮讨论评估（`sonnet在0925的讨论.md`，codex 2026-09-25）

> 该文件包含四类内容：① 资源紧张的建议；②"信息全面但有分寸"→ 审批升级；③ ERP 执行能力；④ 国内 IM/平台生态的外部事实断言。**分类处置**如下。

### 5.1 资源问题 —— 我基本同意，但要纠正一个量化偏差

sonnet 的判断"根子不是内存不够，而是本地 LLM 抢了不该抢的资源"——**方向对，但量级不对**。我实测的数字是：

| 占用方 | 实测 |
|---|---|
| Onyx 9 容器 | **约 7.5 GiB**（OpenSearch JVM 2.1G、background 2.4G、两个 model server 各 1.8G…） |
| ollama `llama-server` | **约 2.5 GiB** |
| WSL 上限 | 12GB（可见 11.7GiB）→ **已经是过载状态，靠 swap 兜着** |

**所以只把 LLM 挪走只省约 2.5G，Onyx 自己那 7.5G 才是大头。** 有效手段按性价比排序：

1. **`wsl --shutdown` 让 `memory=14GB` 生效**（已改好待重启）→ +2GB，且把 swap 清零；
2. **日常开发不常开整套真栈**：sonnet 这条建议与我一直在用的 mock 纪律一致（OEI-003 就立了"mock 跑日常、onyx 跑验收"）；
3. **LLM 提供方解耦（`LLMPort` + `CloudLLMAdapter` / `LocalLLMAdapter`）** —— 这条**在架构上是对的且与本项目既有纪律一致**（我们已经有 `ContentEnginePort` 这个先例）。但它解决的是"别让本地推理成为开发和演示的硬依赖"，**不是**主要的内存解药。作为候选刀，等用户定顺序。

> ⚠️ 一个反直觉但重要的事实：**把 LLM 换成云端 API 会让"离线/数据不出域"这条卖点退后**。本地 Qwen 现在的价值不是质量（3B 召回质量一般），而是**合规叙事**。所以这一步应该是"可切换"，不是"替换"——留本地实现给合规敏感客户，云端给开发和普通演示。

### 5.2 审批升级（"信息全面但有分寸"）—— **采纳，且这正是 ECE 的 IP**

sonnet 的设计（restricted/confidential 查询不直接拒绝，而是触发**有时效、有范围**的临时授权申请 → 审批 → 临时放行 → 全程入审计）与本项目的架构完全同频：

- 判定链、分类矩阵、SQL 下推过滤**都已经在** `permissions/engine.py` 里；
- 缺的确实只是"**申请-审批-时效**"这一层动作；
- 它与我们 OEI-008 立下的"**引擎调用审计**"、OEI-009 要做的 org scope 骨架是同一棵树上长出来的。

**处置**：把"**时间盒 + 范围受限的临时授权**"写成 **OEI-009 的设计要求**（权限模型必须一开始就支持"授权是有期限、有范围的实体"，否则事后加会改模型）；其实现在**后续单独一刀**（候选，暂不编号）。

### 5.3 ERP 执行能力 —— 同意"单独排期、单独护栏"，并且**当前阶段明确不做**

sonnet 的三条护栏（**操作白名单化 / 写操作 human-in-the-loop / 全链路审计**）我全部同意，并补两条：

1. **读与写必须走不同的权限语义**：读走 classification + ACL；**写必须走"提议 → 批准 → 执行"三段式**，且"批准人"这个身份要在审计里可查（正好复用 OEI-008 的 caller 留痕 + OEI-009 的审计接线）。
2. **prompt injection 是这个功能的一等风险**：被篡改的文档里藏指令诱导 Agent 去改 ERP——所以"执行动作"的输入不能只来自模型输出，必须有**结构化的动作契约**（参数受限、可校验）。

**处置**：写入路线图的**阶段说明**——"只读知识助手（权限分层 + 审批升级 + 组织记忆）"与"ERP 执行"是**两个明显分离的阶段**；后者列入"当前阶段非目标"。

该文件对钉钉/飞书/企微的开源动作、OpenClaw 生态、ClawHub 解析技能做了一批**外部事实断言**。我按证据纪律做了核查（负对照：不存在的仓库返回 404 ✓，所以 200 是有意义的）：

**架构层面的建议我采纳**：不要为每个 IM 平台手写集成，而是**照我们已验证的 port+adapter 模式定义一个 `ChannelPort`**，底下接现成实现（OpenClaw 系）——这与 `ContentEnginePort` 是同一纪律。

**但两点必须说明**：
1. **`UNVERIFIED` 的东西不得作为设计前提**（本项目红线）。若将来要做渠道集成，先按我们的证据规则核实到 `CONFIRMED` 再动手。
2. **"顺手用现成解析技能替掉 OEI-007 的管道"这条对本项目不适用**：我们**故意**把文本抽取交给 Onyx 引擎（不引入任何解析依赖，见 OEI-007 §1 与 `DECISION-ONYX.md`）。让 ECE 再背一套解析 Skill，会同时违反"不自研通用能力"和"可替换引擎"两条边界。

### 5.5 商业化结构（可复用 vs 逐客户定制）—— 采纳，登记

sonnet 的这条判断值得写进产品规划："**知识助手核心（权限引擎、组织记忆、context assembly）可跨行业复用；ERP 连接与执行几乎是逐客户定制**，边际成本不会随案例数下降"。→ 登记到路线图的阶段说明，避免将来按"一个案例做好=其余都快"去外推排期与报价。

1. 是否按 §3 的顺序推进（即先签 OEI-008 身份穿透）？
2. 记忆的**范围**：第一版只做"用户级偏好与事实"，还是同时做"组织级记忆"（口径、术语、模板）？后者价值更高但权限模型更复杂。
3. 记忆的**可见性面**：是否要求"本次回答引用了哪几条记忆"在界面上可见（我建议要求——它是可追溯性的直接体现，也是演示亮点）。
