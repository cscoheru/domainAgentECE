# 路径研判（两份外部 review 的综合影响）

> 日期：2026-09-25 ｜ 作者：codex ｜ 输入：`sonnet给ece项目的建议.md`（09-24 夜）+ `sonnet在0925的讨论.md`（09-25）
> 定位：只记**对后续路径的影响**；逐条核实与评估在 `REVIEW-sonnet-assessment.md`。

## 1. 两份文档合起来说的一件事

它们从两个方向撞到同一个结论：**我们这条线的重心应当从"接引擎"转向"做 ECE 自己的那一层"，而那一层的骨架其实已经在了。**

- 第一份（看代码的那份）发现：仓库里**先于 OEI 存在**的 ECE v0 已经有成体系的 identity / permissions / context / audit（含 SQL 下推过滤与真实越权修复记录），OEI 只是加在它上面的"接 Onyx"层。
- 第二份（谈资源与产品的那份）指出：真正决定产品形态的是**权限分层 + 长期组织记忆 + context assembly + 审计**（可跨行业复用），而 IM 渠道接入、ERP 执行是**另一类东西**（integration/execution 层）。

合起来的含义：**"底座"这条路我们已经在走，而且比 OEI 文档呈现出来的更靠前。** 反面是——OEI 这条线如果把注意力过多放在"引擎侧技巧"，会错过真正值钱的那一层。

## 2. 由此固化的三条分层判断（后续设计沿用）

```
① ECE 自有层（IP）：identity / 权限（含时间盒临时授权）/ 组织记忆 / context assembly / 审计 / 来源
② 可替换引擎层：Onyx（内容与检索）——已有 ContentEnginePort 作为边界
③ 集成与执行层：IM 渠道（ChannelPort，候选）/ 企业系统执行（ERP，明确非当前目标）
```

**纪律延伸**：③ 层也必须走 port+adapter（不手写各平台集成），且**外部事实先核实到 CONFIRMED 再动手**。

## 3. 顺序（据两份文档校正后）

```
008 身份穿透 ✔ PASS（谁在问）
 └─► 009 权限与审计接线 ← 关键增量：
         · 结果级权限过滤（CE 无法下推 → 事后过滤的侧信道要处理）
         · org scope 骨架（为 010 组织记忆预留）
         · 引擎调用审计持久化（现为进程内）
         · 「时间盒 + 范围受限的临时授权」写进权限模型（实现可后置）
      └─► 010 持久上下文记忆 v1（用户级 + 组织级，显式记忆）
           ├─► 011 咨询内容补全（36 个种子里 24 个缺行业标签）
           └─► 012 检索质量（3B 召回偏置 + top-k≈2）
                 └─► 候选：LLM 提供方解耦（LLMPort）· IM 渠道（ChannelPort）· 审批流实现
                       └─► 阶段二（另行排期）：ERP 读/执行能力
```

**排序理由**：memory 必须在 permission 之后（否则就是又一个"后置过滤"式越权风险）；org scope 必须在 009 一次做到位（否则 010 被迫改权限模型）；执行能力与只读助手是两个风险等级，必须分开。

## 4. 资源现实影响"怎么做"，不影响"做什么"

实测（见 `DEPLOYMENT-STATUS.md` §9）：Onyx 九容器 ≈7.5GiB 是大头，本地 `llama-server` ≈2.5GiB；WSL 上限 12GB（14GB 待重启生效）。据此固化为 `LOCAL-AGENT-PROTOCOL.md` **§5.1 资源纪律**：日常用 mock、真引擎只用于取证、验完即释放、收尾三查、不默认重跑全套件、重集成考虑按需云 VM。

> LLMPort 解耦的价值定位要准确：**它是"可插拔的合规选项 + 开发期减负"，不是主要内存解药**；且本地实现必须保留（数据不出域是卖点之一）。

## 5. 一句话带走

**别把 OEI 当成"给 Onyx 加功能"的项目；它是"给 ECE 的底座接上一个可替换引擎、并把 ECE 自己的权限/记忆/审计做实"的项目。** 两份 review 的价值，就在于把这个重心校正回来了。
