--------------------------------------------------------------------
§1.1 泄漏根因(读代码 + 现场证据双重确认)
--------------------------------------------------------------------
旧代码的 try: 块从第 155 行才开始(旧行号),而 **uvicorn 的启动与等待在 try 之外**
(旧 132-186 行)。因此:

  `_wait_for_http` 旧实现只 catch `urllib.error.URLError`;
  而 urllib 在 socket 超时抛的是 **`TimeoutError`**,它是 `OSError` 的子类、
  但**不是** `URLError` 的子类 → 逃逸出 `_wait_for_http` → 在旧 132 行的
  uvicorn 等待处直接向上抛 → **旧 155 行的 try 从未进入** → finally(旧 201-212)
  永不执行 → `uvicorn_proc` 成为孤儿进程。

这正是 codex 在 §4 步骤 0 描述的"每次运行泄漏一个 uvicorn",与
`00a-leaked-uvicorn-before.txt`(10 个游离进程,--log-level warning,
启动时刻 15:16/15:19/15:24/15:28/16:30/16:38/17:08/17:14/17:19/17:27
与 10 次 pytest 一一对应)完全吻合。

--------------------------------------------------------------------
§1.2 修法(3 处,全部在"子进程回收"与"skip 前置"授权范围内)
--------------------------------------------------------------------
(a) `_wait_for_http`: `except urllib.error.URLError` → **`except OSError`**
    (OSError 同时覆盖 URLError 与 TimeoutError → 挂起的上游变成 return False,
     走调用方既有的显式分支,而不是抛异常逃逸)。同时移除因此不再被引用的
     `import urllib.error`。
(b) 新增 `_reclaim(proc)`: terminate → `wait(timeout=5)` → 必要时 `kill()` →
    `wait`。幂等(已退出则只 wait)。
(c) 把 uvicorn 启动 / origin 启动 / 冒烟执行**整体**移入 `try:`,并在 `finally:`
    中**无条件** `_reclaim(origin_proc)` + `_reclaim(uvicorn_proc)`
    (反序回收)。两条 skip/fail 分支改为"先 `_reclaim`,再读 stdout"——
    因为子进程持有管道写端,未回收前 `read()` 会一直阻塞到子进程退出。

**断言零改动**:`assert "[PASS] 1." in output`、`assert "FAIL=0" in output`、
`assert "PASS=10" in output and "SKIP=0" in output`、`assert "[PASS] 10." in output`
四条逐字保留。未删除任何测试,未把断言改成"永远通过"。
