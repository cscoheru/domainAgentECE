# ADR-011: Kernel ↔ Runtime 边界 —— Kernel 位于执行运行时与 Agent Harness 之上

- Status: Accepted
- Date: 2026-09-20
- **Amended: 2026-09-20（V3 收口）** — 见文末「修订记录」。本 ADR 的**决策（§1/§2/§4/§6/§7）不变**；**§3（三类接口）与 §5（V0 必须各有进程内实现）的 V0 义务被 `docs/v3/V3_CLOSEOUT.md` §2.4 取代** —— V0 只保留具体实现，不建抽象层；三类接口作为 V1 方向保留。
- Deciders: 产品负责人（创始人）+ AI 架构师（Claude Fable 5.1）
- Phase: V3 — Domain Intelligence Kernel
- 替代说明: **不替代任何既有 ADR**。本 ADR 是 ADR-001（Context Adapter 抽象）在运行时维度的推广。

---

## Context

1. **V2 阶段的 Kernel 定义缺少执行维度。** `docs/architecture_v2/platform-kernel-definition.md` 把 Kernel 定义为"ECE v0 不可省略的最小核心层"，其对照系只有 Glean 一个（Provider 维度）。V2 未讨论 Kernel 与**执行运行时**（workflow engine）及 **Agent Harness** 的关系。

2. **V2 已裁决 Agent Runtime = Partner/Integrate，但未命名运行时基底。** 依据：
   - `docs/research_v2/05-agent-runtime.md:52-58`：通用 Agent Runtime = Partner/Integrate；Domain Agent = 自建；Memory/State = out of v0；Independent Agents / Agent Harness = out of v0（C25 coming soon）。
   - `docs/architecture/agent-runtime.md:3-4`："MVP 自建**薄** runtime，不引入 Agent Framework……runtime 是'领域工作流的执行器'，本身不是 IP；够用、可观测、可替换。"
   - `docs/architecture/glean-x-product.md`：Agent Runtime 的 IP 潜力评为**低**。

   这些结论**方向正确但未命名具体运行时类别**，导致"换运行时"时无接口可依。

3. **V3 引入三个此前不在证据库中的外部系统**（见 `docs/v3/EVIDENCE_V3_ADDENDUM.md`）：
   - **Trigger.dev** [C43]：Durable Workflow / Execution Runtime（Tasks/Runs/Queues/Retry/Waits/Concurrency/Scheduling/Durable Execution/Observability）
   - **DeepSeek Harness (DSH)** [C44]：插件化 Agent Runtime / Harness（Agent Loop/Tools/Skills/Session/Sandbox/Subagents/Storage/Trajectory）
   - **PentAGI** [C45]：领域 Agent 应用（自主渗透测试；多 Agent 监督 + 沙箱执行）

4. **ECE 铁律 3「垂直纪律」明令禁止自研**：消息队列 / 自研 Runtime / 微服务 / K8s，"除非 ADR 明确推翻"。而运行时能力恰好落在该清单上。

5. **ECE `CLAUDE.md` §3.3 规定**："是否引入了新的横向依赖？若是，停下写 ADR。" 引入任何执行运行时或 Agent Harness 均属新的横向基础设施依赖。

6. **治理要求**：本 ADR 的引入方属于类别级能力，`KERNEL_BOUNDARY.md` §9 的"拿掉测试"必须先于选型完成——即在选择任何具体产品之前，先确认 Kernel 在没有任何外部运行时的情况下仍然成立。

## Decision

### 1. Kernel 的定位是业务智能层，不是执行层

> **Kernel 决定"企业应该做什么"；执行运行时决定"任务怎么可靠跑完"；Agent Runtime 决定"Agent 怎么工作"。**

三层职责不可合并。

### 2. Kernel MUST NOT 实现以下能力

```
❌ Queue / Retry Engine / Scheduler / Concurrency Engine
❌ Durable Execution / Checkpointing Engine
❌ Worker Runtime / Task Execution Engine
❌ Agent Loop / Session Runtime / Sandbox / Subagent Runtime
❌ 通用 Tool Runtime
```

以上能力**必须**通过适配器调用外部实现。

### 3. 定义三类接口（ADR-001 的超集）

| 接口 | 职责 | V0 默认实现 |
|---|---|---|
| `ProviderInterface` | 原料：数据与知识 | `InProcessProvider` + `LocalKnowledgeProvider` |
| `AgentRuntimeInterface` | 执行者：Agent 能力 | `InProcessAgent`（单次 LLM 调用，无 loop） |
| `ExecutionRuntimeInterface` | 可靠执行 | `InProcessExecutor`（同步调用，无队列） |

**接口必须 Provider-neutral**：命名用业务语义，禁止出现 `glean` / `trigger` / `dsh` / `pentagi` 等厂商标识符。CI 强制 grep 门禁。

### 4. Execution Intent 是 Kernel → 运行时的唯一契约

```
ExecutionIntent { workflow_spec_ref, context_ref, evidence_requirements,
                  permission_scope, approval_required, proposed_steps[] }
```

**运行时返回 `evidence_candidates[]`，无权直接写入企业事实。** 一切业务事实必须经 Kernel 的 Evidence Layer 转换。

### 5. V0 必须使用最朴素的进程内实现

V0 **不允许**引入任何外部运行时（Trigger.dev / DSH / PentAGI 及其他）。

理由：若 V0 即引入外部运行时，则在验证 Kernel 接口形状之前先引入了集成变量，两个变量同时变化导致无法归因。

### 6. 引入任何运行时依赖必须先写 ADR

本 ADR 是该项治理规则的首次适用。后续每个具体运行时的接入（如"采用 Trigger.dev 作为 Execution Runtime"）须各自另写 ADR，且必须回答**私有化部署可行性**。

### 7. 边界判定测试（四问，缺一即不自建）

```
1. 这是业务语义层还是执行/基础设施层？   → 执行层 → 不自建
2. 成熟实现是否已存在？                 → 是 → 不自建
3. 是否是 V0 闭环必需项？               → 否 → 缓建
4. 是否产生领域 IP（换公司仍可复用）？    → 否 → 不自建
```

## Consequences

### ✅ 正面

- **Kernel 获得类别级稳定性**：具体运行时（Trigger.dev / DSH / PentAGI / 未来其他）可替换、可消失、可新增，Kernel 边界不变。
- **符合铁律 3**：不自研队列/Runtime/微服务，避免与成熟产品正面竞争。
- **降低锁定风险**：延续 `portability.md` 的反锁定论证，从"上下文后端"扩展到"运行时"。
- **归因清晰**：V0 的进程内实现使 Kernel 的失败与集成的失败可分离。
- **私有化优先可检验**：任何运行时接入都必须回答"能否在客户内网运行"。

### ⚠️ 代价与风险

- **接口可能设计过早**：在无真实运行时压力的情况下抽象出的接口，可能形状不对。缓解：接口只定**类别级**最小方法集；V0 用进程内实现验证接口形状；方法可增，签名不宜改。
- **增加一层间接**：所有执行都要经 Intent → Adapter → Runtime 的转换，V0 显得"多余"。接受此代价换取可替换性。
- **运行时的能力差异可能泄漏**：不同运行时能力集不同（如 DSH 有 agent loop，Trigger.dev 有 durable execution），Adapter 需要做能力协商。缓解：`capabilities()` 方法 + 能力不可用时降级为 `unsupported`，而非在 Kernel 内模拟。
- **证据完整性依赖 Kernel 自持**：必须确保 `Evidence → ExecutionRef` 是**仅引用**关系（0:1），运行时消失不影响业务证据完整性。

### 📌 对既有实现的影响

| 影响对象 | 内容 |
|---|---|
| `docs/architecture/agent-runtime.md` 的 `WorkflowEngine` | **降级**为 V0 的默认 `ExecutionRuntimeInterface` 实现，不再是 Kernel 的组成部分 |
| ADR-001 的 `ContextAdapter` | **扩展**为 `ProviderInterface`；11 个方法归入 `context.*`；Mock-first 与 CI 门禁策略逐类复制 |
| ECE v0 `src/ece/` | 需新增 `src/kernel/adapters/`（三类接口定义 + 进程内实现）；`src/ece/` 既有模块不改语义 |
| CI | 新增厂商标识 grep 门禁（扩展到 provider/runtime） |

## Alternatives Considered

| 备选 | 否决理由 |
|---|---|
| **A. 保持 V2 现状**（不定义运行时边界，运行时直接调用） | 换运行时须改 Kernel 代码；与 ADR-001 的"避免不可逆锁定"原则不一致；`agent-runtime.md` 已说 runtime "可替换"，但无可替换的接口 |
| **B. Kernel 内置薄执行引擎并长期演进** | 违背铁律 3；会腐蚀定位（团队精力从"业务推理质量"转向"执行稳定性"）；与红队 §0.7.2「横向 = 死亡陷阱」冲突 |
| **C. V0 直接采用 Trigger.dev** | V0 引入 2–4 周无法消化的集成变量；在私有化可行性未验证前引入外部依赖；违反"先验证接口形状"原则 |
| **D. 采用 DSH 作为 Kernel 的底座** | 混淆 Harness 与 Kernel；DSH 不提供企业 Context / 领域本体 / 数据访问层权限；与 §33 Non-Goals 冲突 |
| **E. 把 Kernel 定义为"更强的 DSH"** | 直接违反 V3 宪法条文（Kernel 不是 DSH，也不与其竞争）；DSH 赛道已充分竞争 |
| **F. 仅定义接口，不规定 V0 实现** | 无进程内默认实现则 Kernel 无法独立运行，"Kernel 在无外部依赖时成立"无法检验 |
