# ADR-006: Context Assembly 12 步流水线自建(ECE 核心架构)

- Status: Accepted
- Date: 2026-09-13
- Deciders: 产品负责人(创始人)+ AI 架构师(Phase 3/4)
- Phase: 4 — Build/Buy/Integrate/Partner

## Context

1. Capability Matrix v2 Row 6 + Phase 3 §4.1:Context Assembly = **Build**(极高 IP)。
2. [C02] Glean 的 Enterprise Context 包含 Context Assembly 能力,但**细节为推导**(STRONGLY_INFERRED);Glean 官方未公开 12 步流水线结构。
3. ECE ARCHITECTURE.md §3 已固化 12 步流水线(identity → resolve → permissions → entities → relationships → documents → structured → temporal → rank → package → provenance → audit),顺序不可变。
4. Context Assembly 是 ECE 区别于"普通 RAG + LLM"的**核心壁垒**:不是检索 + prompt,是企业级任务上下文的结构化打包。
5. PRD #42 明确 Context Specification + Context Evaluation Dataset 是我方 IP 积累方向。

## Decision

1. **ECE 自建 12 步流水线**(ARCHITECTURE.md §3 已固化),顺序不可变,任何步骤失败 fail-closed。
2. **Context Specification**(YAML)作为引擎与领域之间的一级契约(ADR-010 领域包隔离铁律),带 `version`,spec 变更走 git 评审,评测集与 spec_version 绑定(EVALUATION §3)。
3. **Provenance** 每项映射到 `context_items`(DATA_MODEL §5),为 Debugger UI 提供数据源(Sprint 6 实现)。
4. **不模仿 Glean Enterprise Context 全集**:仅实现 ECE v0 任务需要的子集,新任务 = 新 YAML + 必要检索扩展,不改引擎。

## Consequences

- ✅ 12 步流水线可验证、可测试、可审计
- ✅ 新任务/新领域 = 新 YAML(ADR-010 领域包隔离铁律生效)
- ✅ 与 Glean 模式对齐但简化,符合 ECE 垂直纪律
- ⚠️ 12 步顺序固定 — 任何重构需严格 ADR,不能随手改
- ⚠️ spec 版本与评测集绑定,需 git 评审纪律保证

## Alternatives Considered

| 方案 | 否决理由 |
|---|---|
| 仅做检索 + LLM 自由综合 | 不是 Context Assembly,退化为 RAG |
| 借 Glean Enterprise Context 全集 | v3 §0.7 横向上下文平台 = 死亡陷阱,违反铁律 |
| 让 LLM 自组织 Context | 不可验证、不可审计,违反 Permission Before Intelligence |
