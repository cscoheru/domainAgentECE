## 1. 架构成功测试（指令 §37 要求）

**测试方法**：逐个拿掉外部系统，问"Kernel 是否仍然成立"。

| 测试 | 拿掉什么 | Kernel 是否成立 | 依据 | 判定 |
|---|---|---|---|---|
| **Test A** | Trigger.dev | ✅ **YES** | `KERNEL_BOUNDARY.md` 行 14 = Adapter；ADR-011 §5 规定 V0 用进程内执行器 | 通过 |
| **Test B** | DSH | ✅ **YES** | 行 15/16 = Adapter；ECE E1 已证明无 Agent Harness 时 Kernel 可独立产出结论 | 通过 |
| **Test C** | PentAGI | ✅ **YES** | 行 15；它只是可被调用的一类 capability | 通过 |
| **Test D** | Glean | ✅ **YES** | 行 2/3/22/23 皆为 Provider 或"不自建"；ECE v0 已在无 Glean 环境跑通（C47） | 通过 |
| **Test E** | 所有具体 LLM | ⚠️ **架构 YES / 质量 UNKNOWN** | 铁律 5：OpenAI 兼容端点；但国产开源模型实测**未执行**（G-B） | **条件通过** |

**结论**：五项架构测试通过。**但 Test E 暴露一个真问题**：架构上的"模型无关"是廉价的——任何系统只要走 OpenAI 兼容接口都能声称模型无关。真正的考验是**规则引擎覆盖不到的那部分（文档理解、长文本、叙述生成）在国产开源模型上是否够用**。这一项**尚未验证**，且不是架构能解决的。

> **修正建议**：Test E 不应被当作"已通过"，应标注为"**架构通过 / 质量待验**"，且该验证是 GO 的硬前置。

## 2. 指令 §38 的最终判断标准

> **我们是否真的找到了一个不依赖某个特定 Agent、Workflow Runtime、LLM、Glean 或 Connector 的核心产品价值？**

**自检答案**：**架构上找到了，商业上未验证。**

| 维度 | 状态 |
|---|---|
| 不依赖特定 Agent | ✅ 架构成立 |
| 不依赖特定 Workflow Runtime | ✅ 架构成立（ADR-011） |
| 不依赖特定 LLM | ⚠️ 架构成立，质量待验 |
| 不依赖 Glean | ✅ 架构成立（V3 §7.3 理由重心转移） |
| 不依赖特定 Connector | ✅ 架构成立（仅 3 mock） |
| **核心价值在商业上成立** | ❌ **零客户验证** |

**⚠️ 关键诚实声明**：V3 解决的**只是一个架构问题**。它把"产品价值"定义得足够抽象，以至于不依赖任何具体技术——**但抽象本身不是价值**。一个足够抽象的定位，可以把任何东西都说成成立。

**这是 V3 最大的风险**（见 §4 R1）。

## 3. 指令 §39 的 STOP / GO 判定

```
GO 条件：
☑ Architecture Boundary = Clear
☑ Core Objects = Defined
☑ V0 Scope = Small
☑ Runtime Interfaces = Defined
☐ Reference Workflow = Selected          ← 未满足

STOP 触发条件：
✗ Kernel boundary 不清楚              → 否（已清晰，26 行矩阵）
✗ Kernel 与 DSH 重叠                  → 否（KERNEL_BOUNDARY §8 逐项区分）
✗ Kernel 与 Trigger.dev 重叠          → 否（ADR-011 §2 明令禁止实现）
✗ Kernel 与 Glean 重叠                → 否（Provider 定位）
✗ V0 范围过大                          → 否（MVP_SCOPE_V3 §7 规模红线）
✗ Product thesis 不成立                → ⚠️ 未验证（不是"不成立"，是"未验证"）
```

**判定**：**STOP**（不进入 Coding）。两个 GO 条件未满足，且其中"Customer Validation Path"需要真实客户，非文档可解决。

## 4. 对抗性自审：本交付物的真实弱点

以下每一条都是**对本 PRD V3 的攻击**，不是修饰。

### R1 【最严重】V3 用抽象回避了验证问题

**攻击**：V2 把产品定义为"审计证据 Agent"，红队用一个问题就击穿了它（"这是 GRC 平台的一个 feature"）。V3 的应对是把定义上移到 Kernel——**上移到足够高，以至于任何质疑都打不中**。

**具体表现**：
- 问"这个 vertical 有市场吗？" → 答"我们不预设 vertical"。
- 问"护城河够厚吗？" → 答"领域本体 + 证据 + 评估"（皆为未验证假设）。
- 问"客户要吗？" → 答"客户验证是 GO 硬前置"。

**后果**：V3 在**架构上无懈可击，在商业上不可证伪**。这是"用抽象回避验证"，与红队批评 v0.1"超前兑付"属于**同一类错误的另一种形态**。

**缓解措施（已做）**：
- ✅ §5.2 明确"客户验证为零"；
- ✅ §30 把验证列为 GO 硬前置，而非可选项；
- ✅ §36 P8 显式承认"抽象层级升高 → 定位漂移风险"；
- ✅ §4 本条自曝。

**缓解措施（未做，建议）**：**给 V3 设一个时间盒**——若 N 周内 G-A/G-B 未完成，则 V3 的抽象层应被降级回"某个具体候选 vertical + 明确市场假设"，而不是无限期停留在 Kernel 层。

---

### R2 三类接口抽象可能违反铁律 3 的精神

**攻击**：`ece/CLAUDE.md` 铁律 3 明确："任何'以后可能有用'的通用化……一律不做，除非 ADR 明确推翻。"

V3 在 V0 就定义了三类接口 + 三个进程内实现 + CI 门禁。而在 V0，**没有任何外部 Provider 或 Runtime**——这三类接口的另外两种实现方式是空的。

**这是不是"为以后可能有用而提前抽象"？**

**诚实的回答**：**处在边界上，偏向合规但需要警惕。**

支持合规的理由：
1. ADR-001 已经为"单一 ContextAdapter"做过同样的论证，并被接受（Accepted）。三类接口是其**推广**，不是新原则。
2. ADR-011 已"明确"授权（铁律 3 的例外条件）。
3. 接口是**声明**，不是**实现**——V0 的额外成本仅限于三个 Protocol 定义 + 三个薄实现。
4. `mvp-scope.md` 原本就要求 MockAdapter + GleanAdapter 骨架，V3 只是把同一策略扩展到另外两类。

需要警惕的理由：
1. 三类接口在 V0 全部只有一个实现，**无法验证接口是否真的能容纳第二种实现**。
2. 如果 V1 接入 Trigger.dev / DSH 时发现接口形状错误，V0 的抽象就是**负成本**（比不做更贵）。

**缓解建议**：ADR-011 已写明"接口稳定优先于功能完整；方法可增，签名不宜改"。**追加建议**：V0 验收时，对每类接口做一次**"纸面第二实现"压力测试**——用一个假想的 Trigger.dev / DSH 适配器逐方法走查，确认接口能容纳。这比等到 V1 才发现便宜。

---

### R3 Evidence 与 Domain Workflow Specification 的商业价值未验证

**攻击**：V3 把 `Evidence` 和 `Domain Workflow Specification` 立为一级对象，理由是"企业真正被追问的是'这个结论怎么产生的'"。

**但这个理由是推断，不是证据。**

- 没有任何一份客户访谈支持"企业会为可追溯性付费"。
- 红队 v3 反过来指出：审计证据赛道的**真实买家可能是审计顾问/咨询公司**（红队 §一），而顾问的工作方式是否关心 Evidence 对象，完全未知。
- Domain Workflow Specification 尤其可疑：**它有可能是架构师的自娱**——业务专家真的会去读一份 YAML 工作流规格吗？还是他们只关心"结果对不对"？

**缓解措施**：两者都保留在 V0（因为它们成本低且是架构必需），但**必须在客户访谈中显式验证**：
- 问法建议："你们的结论如果由系统生成，你需要看到什么才敢用？"
- 若受访者只关心结论、不关心依据 → Evidence 对象应降级为工程对象，不作产品卖点。

---

### R4 "Glean 是 Provider" 的表述可能过度简化现实

**攻击**：V3 反复强调 Glean 是"可插拔 Provider"，与本地知识库并列。

**但 C03（Enterprise Graph schema 可定制性）是 UNKNOWN**。如果 Glean 的图谱不可定制、不可 API 读写（C03 若为否），那么：

- `GleanProvider` 可能只能实现 `context.search`，无法实现 `context.fetch_relationships`；
- 这会使 Glean 作为 Provider 的**能力显著弱于**文档暗示的"与本地知识库并列"。

**缓解措施**：`PRD_V3.md` §21 已列出 11 方法映射表，但**未逐方法标注哪些依赖 C03**。建议补充：凡依赖图谱 schema 的 method（`fetch_relationships` / `fetch_entity` 的深层属性）标注"**依赖 C03，状态 UNKNOWN**"。

### R5 C43 / C44 的证据强度不足以支撑架构决策

**攻击**：ADR-011 的核心输入是"Trigger.dev 提供 X 能力、DSH 提供 Y 能力"。

**但**：
- C43 的直接原文抓取**被工具限制拒绝**，结论来自检索面摘要；
- C44 **仅有二手来源**（教程/评测类），未取得原始仓库逐字核验；
- C44 自述为 developer preview，能力可能在版本间变化。

**后果**：ADR-011 关于"Kernel MUST NOT 实现 Queue/Retry/Scheduler"的论证，建立在对两个系统的**中等强度**证据上。

**为什么仍然可接受**：ADR-011 的决策是**类别级**的——"Kernel 不应实现执行能力"这一结论，**不依赖 Trigger.dev 的具体能力清单**，而依赖：
1. 铁律 3 的既有禁令；
2. 红队 §0.7.2 的"横向 = 死亡陷阱"；
3. `agent-runtime.md:3-4` 的既有结论"runtime 本身不是 IP"。

**证据等级的诚实标注**：`RUNTIME_COMPARISON.md` §10 已声明局限。**但 ADR-011 的 Consequences 未复述该局限**，建议补一句。

### R6 与 V2 STOP Gate 的一致性未经机械核验

**攻击**：V3 声称"继承 V2 的 K1–K8 + D1，全部 ADR 保持有效"。但本 PRD 由**新的写作会话**产出，**未逐条机械比对** V2 的 STOP Gate 十问答案与 V3 的重新表述是否存在冲突。

**已知风险点**：
- V2 STOP Gate Q10 的答案强调"Permission Before Intelligence / Domain Reasoning / Domain Evaluation"三点；V3 追加了第四点（Evidence 可追溯）。追加不构成冲突，但**需要确认没有弱化前三点**。
- V2 的 `platform-kernel-definition.md:174` 说"Glean 集成作为可选 Adapter"；V3 说"Glean 是 Provider 之一"。**这是扩展还是冲突？** 本 PRD 的处理是"泛化"，但措辞从 "Adapter" 变成 "Provider"，读者可能理解为降级。

**缓解措施**：建议在 V3 审阅时做一次**机械 diff**——逐条列出 V2 STOP Gate 十问的原文答案 vs V3 附录 A 的答案，人工确认无冲突。

### R7 交付物数量多、交叉引用密，存在不一致风险

**攻击**：本次交付 8 个文件，互相引用超过 40 处。任何一处数字或结论变更都需要同步。

**已知的具体风险**：
- 行数/编号（如"26 行矩阵""10 条决策""8 条不变式"）在多个文件中重复出现；
- 证据编号（C43–C48）在 4 个文件中被引用；
- 圆点数字（如"5 暴露 + 5 失败"）在多处出现。

**缓解措施**：已在每份文件头部标注版本与日期；`docs/v3/README.md` 提供索引。**建议**：后续修订时以 `PRD_V3.md` 为唯一事实来源，其余文件只引用不复述数字。

### R8 "Kernel" 命名本身的战略风险

**攻击**：用户指令中说"最终命名可以由 CC 在 PRD V3 中讨论"。V3 直接采用了 **Domain Intelligence Kernel**，未做命名论证。

**风险**：
- "Kernel" 一词在工程语境中已被充分占用（OS Kernel / Kubernetes / Jupyter Kernel），向非技术受众（企业客户、投资人）传达时可能引起误解；
- "Domain Intelligence" 是自造词，无法被搜索、无法被比较。

**建议**：保留 "Domain Intelligence Kernel" 作为**技术定位名**，但**产品对客名称应另行讨论**（可能需要一个更业务化的名字）。本 PRD 未做此事，属**已知空白**。

## 5. 自审结论

| 维度 | 判定 |
|---|---|
| **架构边界是否清晰** | ✅ 是（26 行矩阵 + 5 项拿掉测试 + ADR-011） |
| **是否偷偷做成了 Agent 平台** | ✅ **否**——ADR-011 §2 明令禁止实现 agent loop/session/sandbox；§33 Non-Goals 立法；`MVP_SCOPE_V3.md` §4 排除清单 |
| **是否偷偷做成了 Trigger.dev** | ✅ **否**——队列/重试/调度/持久化执行全部列入 MUST NOT |
| **是否偷偷做成了中国版 Glean** | ✅ **否**——横向搜索/连接器平台/企业图谱实例全部 Provider 化 |
| **是否绕过了验证** | ❌ **部分是**（见 R1：用抽象回避了vertical 与商业验证） |
| **是否有未经标注的过度声明** | ✅ 已尽力标注（C22/C23 反证式、C43/C44 局限、客户验证为零） |
| **是否可进入 Coding** | ❌ **否**——STOP，两个 GO 条件未满足 |

**最终判词**：

> **V3 在架构上完成了它承诺的事：把 Kernel 从"相对 Glean 的最小集"重新定义为"相对任意 Provider 与 Runtime 的业务判断层"，并给出了可执行的边界、对象模型、接口与 V0 范围。**
>
> **但它没有、也不可能解决商业验证问题。而 V3 的抽象层级恰恰使商业验证变得更难启动——因为"我们要验证什么"这个问题本身变得更模糊了。**
>
> **因此本自审的最终建议是：V3 通过架构审阅后，应立即把重心从"完善 Kernel 定义"转向"跑 G-A/G-B/G-C 三个硬前置"，尤其是 G-C（权限硬门，唯一不依赖客户、可立即推进）。**
